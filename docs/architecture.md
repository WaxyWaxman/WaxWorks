# Wax Works — Architecture

**Status:** Specified
**Last updated:** 2026-09-09
**Owners:** sr-talbot, WaxyWaxman

This document is the technical spine. [PRD.md](PRD.md) says what Wax Works is and who it serves; the [flows](flows/) say how each job works; this says how it is built. Decisions here are numbered `A-n` and cited the same way flow decisions are — **don't renumber an existing decision, append instead.**

Several decisions here amend flow documents. Every one is listed in §9 and has been appended to the flow it affects.

**Target:** Vercel + Supabase. First release covers receive → sell → close.

---

## 1. Stack

| Layer | Choice |
|---|---|
| Application | Next.js (App Router), delivered as a PWA |
| Hosting | Vercel |
| Database | Supabase Postgres |
| Authentication | Supabase Auth, one session per terminal |
| UI | Tailwind + shadcn/ui |
| Catalog metadata | MusicBrainz + Cover Art Archive, behind a provider adapter |
| Outbound email | Resend |
| Error tracking | Sentry |
| Background work | A `jobs` table drained by Vercel Cron |

## 2. Decisions

### 2.1 Platform

| # | Decision |
|---|---|
| A-1 | **Online-only in v1.** No offline queue. The PWA caches the app shell; writes fail visibly rather than queuing. Resolves [PRD](PRD.md) §5 *Offline behavior*. |
| A-2 | **Next.js App Router on Vercel.** Till screens are client components; back-office screens are server-rendered. |
| A-3 | **A terminal enrolls; initials attribute.** Each terminal holds a Supabase Auth session whose JWT carries `store_id` and `terminal_id`. The Employee is identified by initials and stamped on every write. Honors [E-01](flows/E-01-authenticate.md)'s no-password trade while giving row-level security a real identity to scope on. |
| A-4 | **Every write is a Postgres `SECURITY DEFINER` function.** The client never writes a table directly. Invariants hold regardless of caller. |
| A-5 | **Every entity is scoped to a Store. Nothing is shared.** Catalog, Suppliers, margins, Sections, the genre map, and sticky retail prices are all per Store. Resolves all five questions under [PRD](PRD.md) §6 *Multi-store consequences*. |
| A-15 | **Money is stored as integer minor units** (`_minor` suffix). ~~Rates are basis points (`_bp`).~~ — **superseded by A-47**: a rate is an integer of parts per million, because a basis point cannot hold QST's 9.975%. No floating point anywhere in the money path — restated by A-47 as an **integers-only** column rule. |
| A-47 | **A rate is an integer of parts per million (`_ppm`), and a rate is applied to an amount exactly once, rounded half away from zero.** **Amends A-15**, whose *"rates are basis points (`_bp`)"* cannot hold the rate the system was always going to meet first: a basis point is 0.01% and **QST is 9.975%**, which [M-06](flows/M-06-settings.md) raised against A-15 rather than working around it. `99750` is QST, `50000` is GST, `600000` is a 60% supplier Discount ([M-01](flows/M-01-supplier-margin.md)), `20000` is the ±2% tolerance ([E-02](flows/E-02-receive-inventory.md) d35). **Everything else in A-15 stands** — money is still integer minor units with the `_minor` suffix, which is what A-36's money columns, A-33a's *reverse as recorded* and §5.1's balance derivations all rest on, and none of them reads a rate. **The no-floating-point sentence gets stronger and is restated as a column rule:** every quantity on the money path is an **integer** — `bigint` minor units and `bigint` ppm — and `real`, `double precision`, and a JavaScript `number` carrying a money figure are all forbidden. That is checkable by looking at a type, where *"no floating point"* was a habit anyone could break in a helper. **One rule covers every rate**, with one exclusion stated rather than left to be discovered: a **currency conversion rate is not covered**, because no rate reaches a stored money figure today — A-36 stores none, [M-05](flows/M-05-accounts-payable.md) reports across currencies separately rather than summing, and both M-05 and [M-06](flows/M-06-settings.md) still carry it as an open question. When exchange gain or loss becomes an artifact, the representation of *that* rate is decided there. **Rounding is half away from zero, once, as each tax is applied** — not at the end — which is [M-06](flows/M-06-settings.md) d16 restated arithmetically. Away from zero rather than toward positive infinity, and nearest rather than ceiling, for two reasons that are not about preference. [E-06](flows/E-06-process-a-return.md) d1 makes a Return a **negative-quantity line**, so a mode that is not symmetric about zero refunds a different figure than it charged and leaves a residue nothing ever notices; and a rate is a **remittance**, not a margin, so rounding that is biased in either direction collects an amount the store does not owe and cannot keep. It also matches the CRA's own convention for GST/HST fractions — nearest cent, up at half a cent — and Postgres `round(numeric)`. The integer form is `(base_minor * rate_ppm + sign(base_minor * rate_ppm) * 500000) / 1000000` under a truncating `bigint` divide. M-06's worked example holds exactly: `$29.99` in Quebec gives `ab` = `$34.48` (GST `$1.50`, QST `$2.99`) and `ab+` = `$34.63` (GST `$1.50`, QST `$3.14`). **Alternatives considered.** *`numeric` with a fixed scale* — rejected, though it is exact and gives Postgres the right rounding for free: `numeric` crosses into the client as a **string**, the till is client components (A-2), and the first coercion of that string puts a double back on the money path, which is the failure A-15 exists to prevent. Integers survive that trip intact. *A numerator/denominator pair* — rejected: exact for any rate forever, and unreadable — a rate stops being comparable, sortable, or enterable as a typed figure on a settings screen, a real cost paid against a precision requirement no recorded rate has. *A special rule for tax alone* — rejected: 9.975% is the tightest requirement in the system and ppm clears it with a digit to spare, so a second scheme would buy nothing and give two places for a rounding rule to drift apart. *Ceiling on every fraction* — rejected: it is not a tie-break but a bias, over-collecting on essentially every line rather than winning as often as it loses, and it is the least symmetric of all the options about zero. *Accepted consequence:* **1e-6 is a ceiling**, and a rate needing a seventh decimal — most plausibly a currency conversion, the one thing this decision declines to cover — is a migration and not a data entry. The same trade [M-06](flows/M-06-settings.md) d16 makes for two taxes per cell, named here for the same reason. |
| A-50 | **The session lapse is a store setting defaulting to 5 minutes, and it is ergonomics only for as long as [E-01](flows/E-01-authenticate.md) has no credentials.** Records [M-06](flows/M-06-settings.md) d45 and **amends A-19a**, which reads *"suppresses E-01's 15-minute session lapse"*, and E-01 d4, whose 15 minutes becomes a default and a shorter one. `store_settings.session_lapse_seconds`, default `300`. **A-19a's substance survives whole:** an **Open** Sale suppresses the lapse on its terminal **whatever the setting says**, so a lapse can never strand a locked Sale mid-ring (E-01 d10, [E-05](flows/E-05-sell-a-record.md) d23). Only the number moved. **The reason this is an A-n and not a settings row is what the lapse does and does not protect.** Under A-3 it is a client-side timer and can be nothing else: what the database trusts is the **terminal's enrollment**, not the initials (E-01 d9), and a lapsed session still sits on a terminal holding a Store-scoped JWT. So the lapse protects **attribution**, not access — setting it to an hour widens the window in which one Employee's initials sit on another's work and widens nothing about what the terminal can reach. That is a defensible thing to let a shop tune, and it is only defensible while it is true. **It stops being true the day credentials arrive** (E-01's open question): a comfort dial becomes an access control, and a shop that set it to an hour will have set an access control to an hour without ever being asked. **This row is therefore to be revisited at that point rather than inherited.** **Alternatives considered.** *Leaving 15 in code* — rejected by d45: a busy counter and a quiet back office weigh accidental misattribution differently, and the lapse measures *inactivity*, so an hour of continuous receiving never prompts either way. *Per-terminal rather than per-Store* — the more accurate answer, since the counter and the receiving desk are the two cases d45 names, and it is recorded nowhere; A-5 scopes to a Store and nothing has asked for finer, so it is noted as not chosen rather than refused. *A maximum on the setting* — **recommended and not taken here**, being the cheapest thing that stops a shop pre-configuring a future access control to an hour; it wants a figure this decision does not have. *Accepted consequence:* E-01 d12 already prompts for initials on the consequential actions regardless of session — opening a Sale, starting a Return, a pay-out, an on-hand adjustment, a void — which is what makes a longer lapse survivable, and is also what will make this setting look harmless right up until the day it is not. |

### 2.2 Catalog

| # | Decision |
|---|---|
| A-6 | **A shared `release_cache` sits underneath the per-Store catalog.** Stores own their own Record rows (A-5); they are populated from a cache shared across Stores, so two Stores never spend two lookups on the same pressing. |
| A-12 | **MusicBrainz is the catalog provider**, behind an adapter. Discogs remains a second implementation of the same interface, off by default. MusicBrainz core data is CC0 and Cover Art Archive is openly licensed, which retires [PRD](PRD.md) §5's Discogs terms-of-use question. |
| A-12a | **The metadata prefetch batches barcodes into Lucene `OR` queries.** MusicBrainz accepts several barcodes per request; Discogs had no bulk endpoint, which is what made a 300-line PurchaseOrder a five-minute job ([M-02](flows/M-02-reorder-inventory.md)). Rate limits are comparable at roughly 1 request/second, and a self-hosted mirror removes the ceiling if it ever bites. |
| A-14 | **Cover art is a stored URL, not a stored file.** `records.cover_art_url`, with a nullable `cover_art_path` reserved so a later snapshot job needs no migration. |

### 2.3 Governance — flags, not gates

| # | Decision |
|---|---|
| A-28 | **The manager override is replaced by a review queue.** Actions previously gated behind an override — below-cost shelf pricing, Invoice adjustment beyond ±2%, subtotal discrepancy, selling into negative inventory, breaking a sale lock — now proceed, and write a `review_flags` row that a Manager reviews afterward. Amends [PRD](PRD.md) §2.2 and [M-04](flows/M-04-manage-users.md), and closes M-04's *Audit surface* open question. |
| A-28a | **Manager-only is unchanged.** Adjusting on hand, voiding a finalized Invoice, Undo End of Day, accounts payable, settings, ~~deletions~~, merging Suppliers, and setting a supplier margin remain gated — **plus, added by A-54, processing pending orders into PurchaseOrders, voiding a PurchaseOrder, and abandoning or voiding a claim**, which were gated in their own flows and missing here, **and, added by [M-04](flows/M-04-manage-users.md) d17, acknowledging a ReviewFlag** — which §6 has gated as `review_flag_acknowledge` **M** since A-28 while this list has never named it, so the gate existed in the function surface and in no specification. **M-04 d11 and d14 also settle what this row could not:** *is there a tier above Manager* is answered **no**, so *manager-only* is the top of the role model and nothing outranks it. *Deletions* is **superseded by A-54**: deletion is gated by **state**, not by role. A Manager authorizes in place by entering their own initials; both names are recorded. The [lexicon](lexicon.md) distinguishes *manager override* from *manager-only* — only the first is replaced. |
| A-48 | **The ±2% tolerance is a bound in the receiving write path, and it leaves the review queue.** **Amends A-28**, whose action list still names *"Invoice adjustment beyond ±2%"* among the things that proceed and raise a flag, and **amends §5.2**, whose `kind` enum still carries `invoice_adjustment`. [E-02](flows/E-02-receive-inventory.md) d50 makes the tolerance a **wall at the Invoice Total and nowhere else**, and [M-04](flows/M-04-manage-users.md) d10 removes the row from the review queue rather than leaving it describing something that cannot happen. **This is not the manager override returning.** A-28 replaced gates that *waited for a Manager*; a bound waits for nobody, no authorization lifts it, and it does not join A-28a's set. **Where it is enforced is the whole of the decision.** Under A-4 the bound is asserted inside the definer function that writes the Total — `invoice_finalize` and every correction path against a finalized Invoice, which already call `invoice_is_paid()` under A-41 — and never in the screen: a bound enforced in the client is not a bound, and E-02 d50's own reason is that the flag is seen after the fact while the wrong total is what everything downstream reads. **It bounds one field.** The stated subtotal from the supplier's paperwork (E-02 step 6), tax, freight and miscellaneous stay freely enterable, so a genuine lump difference is recorded as the charge it is; d18's derived-versus-stated comparison stays a warning the Employee may accept, which still raises a flag. `20000` ppm is the figure, as A-47 names it. **Alternatives considered.** *Making the tolerance configurable* — refused by [M-06](flows/M-06-settings.md) d43: it is a governance threshold rather than a shop preference, and a tolerance on a settings screen is an oversight control a shop can quietly switch off. *Keeping the flag as well as the bound* — rejected: a `kind` that can never fire is a queue entry nobody will ever see, and an enum value with no producer is drift with a comment on it. *Bounding tax, freight and misc too* — rejected for E-02 d50's reason: the figures printed on a supplier's paperwork must always be enterable as printed. *Accepted consequence:* receiving loses its escape hatch, and an Invoice that genuinely cannot be reconciled at the counter is finished in accounts payable by a Manager raising an Adjustment ([M-05](flows/M-05-accounts-payable.md) d12) rather than by whoever is holding the box. **The [lexicon](lexicon.md) now has two entries that are wrong** — *±2%* ("a threshold at which a Manager is told, not a wall") and *CostAdjustment* — which were true of every use of the tolerance until this row and are true of none of them now. |
| A-52 | **A settings write is a definer function like any other write, and it is logged with its actor.** Closes a gap rather than changing a rule: A-4 already makes every write a `SECURITY DEFINER` function and A-28a already makes settings manager-only *"with both names recorded"* — but §6 carried **no Settings domain**, and [M-06](flows/M-06-settings.md)'s Requirements impose **no log**. So today, changing a tax rate, a Section's `returnable` flag, the price ending or the tender list has **no recorded actor anywhere**, while [M-01](flows/M-01-supplier-margin.md) d4 logs every edit to a Supplier's card. **This session is what makes the gap expensive.** Settings used to hold names and lists; they now hold the **tax rates** every Sale resolves through (M-06 d11), the **nickel rounding** that decides what the drawer takes (d21, d26), and **discountability and returnability** on instruments equivalent to cash (d30). A money rule nobody is recorded as having changed is worse than a money rule in code, because code has a commit and a reviewer. **The surface.** A `settings_*` function per configuration group — tax types and groups and cells, product tax codes, tenders, Sections, genres and the map, currencies, store details and the `store_settings` keys — every one **M** under A-28a, every one appending a `settings_log` row carrying actor, timestamp, the key touched, and the values before and after. **Before and after, not just after**, because the question asked afterwards is always *what did this used to be*, and M-06 d8's never-retroactive guarantee means the old value is the only record of what yesterday's Sales were computed against. **Two writes are exempt and only two:** the Store ID and Store position (M-06 d47), which no function offers because no actor may set them — see §11. *Accepted consequence:* a settings screen that saves on blur, as [M-01](flows/M-01-supplier-margin.md) d13's Supplier card does, will write a log row per field rather than per visit, and the log wants reading by key rather than by session. That is the trade M-01 d13 already made and named. |
| A-54 | **Deletion is gated by state, not by role: it is refused while live references exist, and it never removes a historical row. Amends A-28a**, whose unnamed *"deletions"* category is replaced by this rule, and **closes the contradiction** [M-01](flows/M-01-supplier-margin.md) recorded and declined — A-28a gated deletions while [E-07](flows/E-07-manage-customers.md) d12 made every Customer action ungated, Delete included. **The role gate was solving the wrong problem.** A Manager deleting a Supplier who is owed money does exactly the same damage as an Employee doing it; requiring permission for a destructive act is weaker than making the act impossible, and A-4 already says where an invariant belongs. **Refused while live references exist**, enforced in the definer function and not in the screen: a **Customer** with a non-zero account balance, a Held Sale, or open customer-attached order lines; a **Record** with sellable or held copies on hand or outstanding PurchaseOrder lines; a **Supplier** with outstanding accounts payable, a draft Invoice, an in-flight claim, or a pending order stream. Every one of those is already derived and already on screen — they are the *in-flight* tracks [M-01](flows/M-01-supplier-margin.md) d14 and [E-07](flows/E-07-manage-customers.md) d19 specify, so the check is a query the cards already run. **The balance case is the one that names the reason:** deleting a Customer who owes the store money erases the debt along with the debtor, which is not a data-integrity problem but a fraud path. It is cleared to zero first, or not at all. **Deletion never removes a historical row.** A past Sale keeps every line it ever had and loses only its **link** — [E-07](flows/E-07-manage-customers.md) already says so (*"Past Sales keep their own record of what happened; they simply no longer point at a Customer"*), [E-04](flows/E-04-manage-inventory.md) says the same for a Record because line values are snapshotted ([E-05](flows/E-05-sell-a-record.md) d13), and this generalises both: the reference is nulled, the row is not touched. That is what makes deletion survivable at all, and it is why this rule can be structural rather than a permission. **Where no live reference exists, each flow's own rule stands** — ungated for a Customer ([E-07](flows/E-07-manage-customers.md) d12 survives whole), Manager for a Record ([E-04](flows/E-04-manage-inventory.md)). [M-01](flows/M-01-supplier-margin.md)'s open question **narrows rather than closes**: what remains is only whether a Supplier with nothing in flight is a Manager's to delete, and the destructive case is now impossible at either answer. **This also closes [E-04](flows/E-04-manage-inventory.md)'s *who may delete a Record with stock on hand*** — nobody, at any role, until the stock is gone. **And A-28a's list gains the four actions it was missing**, all of them already gated in their own flows: processing pending orders into PurchaseOrders and voiding a PurchaseOrder ([M-02](flows/M-02-reorder-inventory.md)), abandoning a claim ([E-04](flows/E-04-manage-inventory.md) d24) and voiding one (d27, d29). **Alternatives considered.** *A-28a wins and Delete becomes manager-only everywhere* — rejected: it reverses a deliberate design intent, since [E-07](flows/E-07-manage-customers.md) made Customers ungated on purpose and deleting a duplicate typed in twice is not destructive. *The flows win and A-28a drops deletions entirely* — rejected: it leaves the destructive case unguarded at every role and leaves M-01 undecided, which is the state that produced this contradiction. *Deactivate rather than delete, as Users and settings do (M-04 d5, M-06 d9)* — **rejected narrowly and worth recording:** it is the house pattern and it is right for anything whose identity must survive for attribution, which a User and a tax type are and a duplicate Customer is not. A shop that cannot remove a typo accumulates typos forever. *Accepted consequence:* deletion now fails for a reason the operator has to go and fix elsewhere — clear the balance, sell or write off the stock, settle the payable — so the refusal has to say **which** reference blocked it and link to it, or it reads as the system simply refusing. |
| A-55 | **User administration is three manager-only definer functions in the Identity domain; its two invariants split between a partial unique index and a function assertion under a lock; and "immediately" is a property of the write path, not of the browser.** Closes the gap [M-04](flows/M-04-manage-users.md) d13-d16 opened: §6's Identity domain carries `terminal_enroll`, `actor_resolve` and `manager_authorize` and **no way to add, re-role or deactivate a User at all**, so four just-ratified invariants have no enforcement point. **The surface.** `user_add` **M**, `user_change_role` **M**, `user_deactivate` **M** and `user_reactivate` **M**, in **Identity** rather than a new domain, because §6 groups functions by the thing they write and Identity already writes the `users` row. There is **no delete function**, which is how M-04 d5 is enforced: nothing is refused because nothing is offered, the move A-54 made for the Store identifiers. **All three join A-28a's list, and this is the most urgent part of the row.** M-04's manager-only table names none of them while its d2 makes anything unlisted an Employee action — read literally, an Employee may create a User and promote themselves to Manager. That is the same omission d17 closed for `review_flag_acknowledge`, except here the unlisted action *is* the privilege boundary. A-54's *gate by state, not by role* pattern expressly does **not** substitute: there is no state that makes granting Manager harmless. **Initials uniqueness is declarative** — a partial unique index on `users (store_id, initials) where active`, carrying M-04 d13 as amended by d16 and d20, **over initials normalised on write — trimmed and upper-cased** (M-04 d20), so the index is a plain unique index and no shift key can mint a near-duplicate at the counter, for the reason A-36's composite keys and A-44's void keys both give: unrepresentable beats remembered. The function still traps the violation, because d13 requires the Manager to resolve the clash on the spot and a bare constraint error is not that refusal (A-54's *say which reference blocked it*). **The last-Manager floor cannot be a constraint at all.** It is a per-Store aggregate across rows, so no row `CHECK` and no index can hold it, and a stored count is refused by §5.1's no-running-totals rule and A-35. It is a function assertion and **the lock is the whole of it**: `user_change_role` and `user_deactivate` take the Store's active Manager rows `FOR UPDATE` in primary-key order (A-38's ordering) and re-count under the lock. Without it, two Managers demoting each other concurrently both read a count of two and both commit — A-37's two-settlements-one-credit failure with a role in place of money. Promotion only raises the count and locks nothing. **A role change resolves at call time.** M-04's *takes effect on the next session* governs what the shell draws and nothing else; every manager-only function resolves the authorizing initials to an **active Manager row at the moment of the call**, because a write path honouring a role the client is holding is §5.1's invariant enforced only in the screen. §6 has never said `manager_authorize` checks that the authorizing person is active and holds the role; it says so now. **"Ends sessions immediately" is corrected rather than implemented.** Under A-3 and A-50 a staff session is client state — an actor and a timer in a browser — and what the database trusts is the terminal's enrollment (E-01 d9); A-50 says the lapse *"is a client-side timer and can be nothing else"*. There is no session row, so no write can end one, and **[M-04](flows/M-04-manage-users.md) d15 and E-01's inherited bullet overclaim as written**. What is achievable is what d15's own next sentence asks for: `actor_resolve` refuses an inactive User, every definer function resolves through it rather than stamping a string, and from the instant the deactivation commits **no new work can be attributed to that User anywhere**. The shell re-resolves its actor on the cadence it already reads `store_settings` for (A-50), so the screen catches up within one interval. Immediate where it is enforced, eventually consistent where it is drawn — and under A-1 a terminal that cannot reach the server cannot write, so the refusal cannot be dodged by going offline. **Resolution is by `user_id`, which amends §3 and §6's *every function takes `p_actor_initials`*.** M-04 d16 releases initials to a new hire, so the same string resolves to a different person over time: a stale client posting `JD` would be attributed to the **new holder**, and a revocation check asking *is `JD` active* answers **true** the moment the initials are reused. So the session resolves once to a `user_id`, the shell re-resolves that id, and every write carries it alongside the initials it was resolved from. `actor_resolve` is the only place a string becomes a person. **Reactivation is a fourth function and it is where the index bites hardest.** M-04 d19 gives a returning employee their original User row back rather than a second one, which d5 requires — but d16 released their initials and a new hire may be holding them, so `user_reactivate` **prompts for new initials on a clash** exactly as `user_add` does, rather than refusing and sending the Manager to re-initial somebody else. **The Open Sale carve-out is part of the check, not beside it.** d15 keeps an Open Sale finishable, so the refusal is not blanket: the Sale functions accept an inactive actor **only** for a Sale already **Open** and locked to them (§5.3); everything else refuses. **A deactivation is logged, not flagged.** `users` carries a `log`, the column A-35 already mirrors from Invoices and Suppliers, appended by all three functions with actor, authorizing Manager, timestamp and the values **before and after** — A-52's reasoning transferred whole: without it, who promoted whom exists nowhere after the second change, and this is the privilege boundary rather than a tax rate. **Not a `review_flags` row**, because a ReviewFlag records that an *Employee* acted and all three of these are manager-only, so it would be a Manager flagging themselves. **Not `settings_log`**, which A-52 keys by configuration group and key; a User is not a configuration key. **Milestone: M1, and this is A-53's split exactly.** §8's M1 already builds Users, RLS and the authorization functions, and §7's `seed.sql` already writes Users — so without the index and the floor in M1, the first migration can seed a Store with no Manager and duplicate initials. **The Deactivate and Add screens move forward, ahead of [M-06](flows/M-06-settings.md)'s settings screens** (M-04 d21, amending §8): while E-01 has no credentials, deactivation is the only access control the shop has, and a revocation that requires a support call is not one. The rest of M-04's administration stays where §8 puts it. **Alternatives considered.** *A separate Users domain* — noted, not chosen: it splits one table's writes across two rows of a table organised by what is written. *Uniqueness enforced only in `user_add`* — rejected on A-36's reasoning; a partial index costs nothing and protects callers that do not exist yet. *A trigger for the floor* — rejected: §5.1 keeps triggers for local facts on the row being written, and a cross-row aggregate would still need the same lock inside the trigger. *A stored `active_manager_count`* — rejected by §5.1 and A-35. *An Owner tier permitted to breach the floor* — already refused by M-04 d11 and d14, not reopened. *Realtime revocation* — rejected for v1: near-instant, but it makes a v1 dependency of the mechanism §4 reserves for the post-v1 print agent, and a dropped socket fails silently unless the write-path check exists anyway, which it does. *Revoking the terminal's Supabase Auth session* — refused: under A-3 that session is the **terminal's** and is shared, so it would unenroll a whole counter to remove one person. *Deferring the surface to the post-v1 M-04 milestone* — rejected: while E-01 has no credentials, deactivation is the **only** access control the shop has, and a shop that cannot revoke a departing employee is worse than A-53's shop that cannot change its own tax rate. *Accepted consequences, and there are four.* **(1)** *Immediately* now means two latencies in one sentence, and both flow documents have to carry both. **(2)** Until the M-04 screen ships, adding and deactivating a User is a call the WaxWorks team makes on the shop's behalf — and staff turnover is more frequent than a tax-rate change, so this is A-53's consequence in a sharper form; M-04 d21 resolves it by moving the Deactivate and Add screens ahead of M-06's, so the window is the length of M1 rather than the length of v1. **(3)** `user_add` is itself manager-only, so a Store reaching zero active Managers by any route the floor does not cover has **no in-product recovery** — M-04 d14 names this and this row makes it structural. **(4)** A deactivated User's Open Sale stays writable under their initials until somebody finishes it or breaks the lock, and an Open Sale suppresses the lapse whatever the setting says (A-19a), so that window has **no expiry** |

### 2.4 Selling

| # | Decision |
|---|---|
| A-11 | **Sale numbers are unique per Store**, allocated from a locked counter row. [E-05](flows/E-05-sell-a-record.md) d2's "globally unique" was contrasting Sale numbers against supplier Invoice numbers, which are keyed per Supplier; it predates the multi-store decision. |
| A-16 | **A Sale has a fifth state, `open`** — pre-tender, carrying no Sale number and absent from [M-03](flows/M-03-daily-summary.md) reporting. E-05 assigns *Current* only on completion of tender, which left the Sale being rung up unnamed. |
| A-17 | **Gapless numbering uses a locked counter row, not a Postgres sequence.** `store_counters`, read `FOR UPDATE` inside the allocating function. A sequence gaps on every rolled-back transaction, and E-05 d4 treats a gap as missing paperwork. Counters: `sale_number`, `hold_ref`, `internal_barcode`, `invoice_number`. |
| A-19 | **An `open` Sale is locked to the Employee who opened it.** Handing it over requires putting it on Hold; any Employee may re-open a Held Sale, which transfers the lock. **Tender is attributed to the current lock holder.** Closes E-05's *Employee attribution vs. Sale ownership* open question. |
| A-19a | **An `open` Sale suppresses E-01's 15-minute session lapse** on its terminal, so a lapse can never strand a locked Sale mid-ring. Answers E-01's open question on whether the lapse applies during an open Sale. |
| A-23 | **Held Sales are absent from the close.** `close_run` touches only Current Sales — a Hold is not revenue until tendered. Held copies still reduce *available* stock, so the summary's stock position reflects them. Closes M-03's open question. |
| A-25 | **A deposit uses the customer ledger, not a new Sale state.** A Sale with no lines, tendered to the Customer's account, creates the credit; the Held Sale displays that balance. Closes E-05's *Layaway / deposits* open question using machinery that already exists — `sale_tender` accepts zero lines, as the `$0.00` Used Credit counter buy already required. |
| A-51 | **A GiftCard is a code and a movement history; its balance is the sum of its movements and is stored nowhere.** Follows A-20a, A-33b, A-35 and §5.1's derived on hand for the reason all four give: **nobody sets a gift card balance**, so a stored figure would be a second copy of a fact the schema can answer, with a release path someone has to remember. §5 already carries `gift_cards` and `gift_card_movements`; this row says what they mean. Both are composite-keyed on `(store_id, …)` (A-36), and a card belongs to one Store (A-5). **The movement rows, named rather than left to be invented.** A `load` (+), sourced from the **SaleLine** that sold it — [M-06](flows/M-06-settings.md) d18's system-owned non-tracked catalog entry, so a load resolves genre → product tax code like every other line and tax has no special case. A `redeem` (−), sourced from the **Tender** row ([E-05](flows/E-05-sell-a-record.md) d10). A `reversal` (±), sourced from the Sale **void or edit** that struck that line or that tender (E-05 d31, d32). There is deliberately **no `adjust` kind and no manager write path in v1**: value moves two ways and both already have an artifact, and a hand-set balance is the thing A-35 refuses. Every movement carries actor initials and a timestamp (§3) and its own currency code (A-36); a card is denominated in the Store's home currency ([M-06](flows/M-06-settings.md) d34). **Enforcement, which is the load-bearing part.** `Σ movements ≥ 0` per card is not expressible as a table constraint, so **`sale_tender` is its only enforcement point** — it takes the card row `FOR UPDATE` and re-evaluates under the lock, the same discipline §5.1 requires of `ap_settle` for a credit. **A-37 is precedent for *derive it*, not for *there is nothing to bound*:** a credit is consumed **whole**, so A-37 could retire the arithmetic and keep only the lock; a gift card is explicitly **partial** (E-05 step 10's split tender), so here the arithmetic and the lock both stand. A redemption that would drive the sum below zero is **refused, never clamped**: clamping converts an over-redemption into a silent loss, which is what the prototype does today. **The liability registry** ([M-05](flows/M-05-accounts-payable.md) d10) is a **view** over movements — A-38's rule that balances are views, so reads go straight to row-level security. Code and Customer from `gift_cards`; current balance `Σ amount`; issue date `min(created_at)`; last-used `max(created_at)` of a `redeem`. **M-05's registry was silent on stored-versus-derived** — it lists report columns, all of them derivable — so this row settles it rather than contradicting it. **What it binds and what it leaves alone.** E-05 d10 is unchanged — loading is a line, redeeming is a tender; only what they *write* changes. E-05 d32 is what this makes safe: striking a settled gift-card tender becomes an **appended reversal**, so a second void cannot credit twice and nothing has to be flipped back. **[M-06](flows/M-06-settings.md) d30's `returnable = false` stands**, and this row answers only half its reason: a Return of a load is now *arithmetically* representable and boundable by the card's current balance, so the over-refund objection goes — but d30's actual reason is that a Return under [E-06](flows/E-06-process-a-return.md) d3's no-receipt, no-time-limit, no-approval rule is a **cash-out dressed as a refund**, and d4 settles a refund to cash or store credit. The movement model does not touch that. **Relaxing d30 therefore needs a decision about gating, owned by M-06 and E-06, and this row must not be read as having granted it.** **Alternatives considered.** *A stored balance with a movement log beside it* — rejected for A-33b's reason exactly: d32's reversal has to put value back, and a stored figure is a thing to flip while a movement is a row to append; two copies drift, and the one that drifts is the one the store owes. *A running balance maintained by trigger* — rejected by §5.1's no-running-totals rule, and because it would be a second enforcement point for an invariant `sale_tender` already holds under a lock. *Deriving the card's existence too, with no `gift_cards` row* — rejected: a card is scanned **before** it is loaded (E-05), so the code must resolve to something, and A-43 wants a system-written `created_at` for *issued* to key on. This also retires the prototype's conflation of `balance = 0` with *not yet loaded*, which re-offers a load on a spent card. *Accepted consequence:* the registry's total is an aggregate over every movement the Store has ever written and grows without bound, so it wants an index on `(store_id, gift_card_id)` before it wants anything else; and **a card is a Store's liability, not the chain's** — a sister Store cannot honour it. That is A-5 holding, and it is the first place a customer will notice A-5. **Two questions stay open beside this and are not closed by it:** expiry and escheatment (E-05), which a movement history makes an appended negative rather than a flag and therefore forecloses nothing; and E-06's *store credit issued without a Customer*, where issuing a card in place of cash would be a positive movement with no Sale line behind it — representable, and not authorised here. |

### 2.8 Payables

| # | Decision |
|---|---|
| A-36 | **The Payables data model.** The group becomes `supplier_claims`, `ap_ledger_entries`, `ap_credits`, `ap_payment_batches`, `ap_payment_batch_voids`, `ap_payment_targets`, `ap_clearings`, `ap_clearing_members`. **`ap_payments` is retired** — it named APPayment's shape, which the [lexicon](lexicon.md) already retires and which [M-05](flows/M-05-accounts-payable.md) d16 replaced with a PaymentBatch carrying typed targets (d19). **A void is a row, never a column:** A-33a forbids updating the batch, so `voided_at` on the batch would break the rule the void exists to honour, and `unique(batch_id)` on the void table makes a double void structurally impossible rather than a check someone remembers. **An Invoice's balance owing** is its reconciled Total — tax **included**, because A-29 takes tax out of *cost of goods*, not out of what is owed — less every target against it in a non-voided batch, of either kind. **A Supplier's balance** is four terms: debits, less money targets, less claim-credit targets, less credits that are **agreed** (d26) and **not consumed**. The fourth term is what makes d26's *"applying a credit never moves the balance"* arithmetically true; drop any term and one of M-05's worked examples breaks. **Both balances may be negative**, on the same footing as on hand in §5.1 — a negative Supplier balance means the supplier owes the store, and nothing clamps it. Every money column is integer minor units (A-15) and **carries its own currency code**, because A-33a requires a void to reverse amounts *as recorded* and that is undefined without one; no rate is stored, so exchange gain or loss stays M-05's open question. Every foreign key is **composite on `(store_id, …)`**, making a cross-tenant reference unrepresentable rather than merely policy-prevented — which matters because A-4 puts these writes in definer functions where row-level security does not apply. The same trick on `(supplier_id, …)` turns d7's same-supplier rule into a declarative constraint. **One remainder per source credit** (d25, d28), so provenance is a single reference and a void reverses each independently. *Accepted consequence:* the ledger grows a row wherever it used to mutate one, and a credit's history is a chain rather than a field. |
| A-37 | **A credit's terminal states are derived from artifact rows, never stored on the credit.** Completes [M-05](flows/M-05-accounts-payable.md) d24 and d28, which removed a credit's running remainder without saying what the binary fact they left behind is made of. A credit is **consumed** when a claim-credit target in a non-voided batch names it, and **cleared** when it is a member of a non-voided clearing. There is no `applied`, no `remaining`, no `consumed_at`, no `cleared_at` and no state enum. Two reasons, the second decisive. **They are not one fact:** consumption moves money, clearing is explicitly balance-neutral (d15, d27), so an enum would force two axes into one column and make illegal combinations representable. **And a stored flag has a release path someone must remember:** d22's void returns a credit to un-consumed exactly as A-33a returns an Invoice out of Paid, and A-33b refused a stored `paid` for that precise reason — there is nothing to flip. Follows A-20a and A-35: the schema already answers both questions from rows, and a second copy drifts. **Corrects d24's reasoning.** Whole consumption retires the *arithmetic* — there is no sum to bound — but **not the row lock**. Two settlements can each read a credit as un-consumed and each attach it at full value, which is worse than over-spending a remainder. The invariant that replaced `sum(applications) ≤ amount` is an **equality** — a credit's targets plus the remainders emitted from it equal its amount — which no table constraint can express, so `ap_settle` is its only enforcement point. *Accepted consequence:* "is this credit spent" is a query across two tables rather than a column read, and mutual exclusion lives in one function's lock discipline rather than in the schema. |
| A-38 | **The payables function surface and its locks.** `ap_payment_record` is replaced by **`ap_settle`**, which takes [M-05](flows/M-05-accounts-payable.md) d27's selection whole: it writes the batch, one target per debit and kind, any placeholder disposals, and — in the same transaction — emits the remainder Credits d28 requires, asserts A-37's equality, re-evaluates A-33b for every Invoice it touched, and returns any flags raised. All or none, in the shape §6 gives `sale_tender`. **`ap_batch_void`** appends the void artifact, never updating the batch (A-33a), restores every credit by the *absence* of a live target rather than by a write, reverses the remainders this batch emitted, and **refuses** where one has already been absorbed or cleared (d22, d24). Manager-only under A-28a, with both names recorded, as are `ap_entry_create`, `ap_clearing_create` and `claim_mark_credited` — the last now a **money write**, since d26 makes a Credited claim count. `claim_create` stays an Employee action: the claim is raised in [E-04](flows/E-04-manage-inventory.md), not here. Balances are **views**, not functions, so reads go straight to row-level security as §3 requires. **Locks:** every credit and every debit in the selection, `FOR UPDATE`, **in primary-key order** so two Managers ticking the same rows in opposite screen order cannot deadlock; nothing locks the Supplier row, because the balance is derived and stored nowhere. *Accepted consequence:* a settlement holds locks across several tables for one transaction — acceptable at a few payment runs a week, and not a pattern to copy at till volume. |
| A-39 | **Payables moves ahead of M-02, and the Invoice immutability trigger moves out of M3.** Amends §8. The trigger fires only on a **paid** Invoice (A-33), and no Invoice can become paid before payables exists — so in M3 it can neither evaluate A-33b's predicate nor guard anything. §8's M3 entry is a leftover from the pre-A-33 reading where the trigger fired at finalize. It moves to the payables milestone alongside the tables its predicate reads, which **closes §11's one blocking open question** rather than restating it. M3 keeps no immutability work: §5.1's other two immutable things belong to M4 and M5. Payables also needs two things §8 scheduled nowhere — **E-04's SupplierClaim tables**, which d26 makes a balance input, and **M-01's payment terms and billing address** with E-02 d45's derived due date, without which nothing can be called overdue. *Accepted consequence:* M-02 reorder slips behind payables, and the claims screen arrives earlier than the flow that raises most claims would suggest. |
| A-40 | **`SECURITY DEFINER` functions re-assert the tenant.** Answers §11. A-4 makes every write a definer function, which therefore does **not** get row-level security applied to its own statements, so §5's policy protects tables the function bypasses. Every definer function resolves `auth.store_id()` itself and carries it in every predicate and every insert, and `search_path` is pinned on every one. **General, not payables-specific** — but payables is where it bites, because `ap_settle` takes client-supplied ids for Invoices, entries and credits at once and writes five tables. A-36's composite `(store_id, id)` foreign keys are the belt to this braces: they make a cross-tenant reference unrepresentable at insert time, independent of what any function remembers to check. *Accepted consequence:* every existing function has to be revisited against this rule rather than only the new ones. |
| A-41 | **An Invoice's immutability is a check in the write path, not a trigger.** **Supersedes the second half of A-39** — there is no Invoice immutability trigger to move, because there is no trigger. `§5.1` had made immutability *a thing to build*, which is why it needed a milestone and why it collided with payables not existing yet; making it a property of the write path dissolves the collision instead of rescheduling around it. **`invoice_is_paid(invoice_id) → boolean` is the single seam.** Every E-02 write path against a finalized Invoice calls it and refuses while it is true; `ap_settle` and `ap_batch_void` call the same function when they re-evaluate (A-38); the screens call it to decide whether to draw the scan slab. A-33b's predicate therefore has exactly **one** definition, which is also what gives the corrections-racing-settlements lock in A-33b something single to lock around. **M3 ships it returning `false`** — correct rather than stubbed, since no Invoice can be paid before payables exists — and the payables milestone replaces the body with the real derivation. No migration moves, no deliverable is rescheduled. **This covers the Invoice only.** §5.1's other two immutable things — SaleLines on Closed Sales, and voided Sale numbers — keep their triggers: neither spans tables, neither has a timing problem, and a local trigger on a local fact is the cheapest enforcement there is. *Accepted consequence, and it is the reason §5.1 said "trigger" in the first place:* a write-path check protects the write paths that exist. A migration, a manual fix, or a function added in two years by someone who does not know the rule can edit a paid Invoice with nothing to stop it. A-4 narrows that gap — every write is a function, so there is no client path to forget — but it does not close it, and this decision accepts the remainder knowingly rather than by omission. |
| A-42 | **`ap_batch_void` appends a reversing Adjustment and never refuses.** **Supersedes A-38's refusal clause** and records [M-05](flows/M-05-accounts-payable.md) d30 at the function surface. A-38 had the void refuse where a remainder it emitted had since been absorbed or cleared, which made void legality **order-dependent along a chain of batches** — voiding batch 1 refused while batch 2 held its remainder, and became legal once batch 2 was voided. It also had the void **delete** the remainder, the one place in the whole design where undoing something destroyed a row. Both go. The void now appends a system-sourced reversing Adjustment for every remainder the batch emitted, which restores the Supplier's balance whether or not the remainder still exists, so the function has no refusal path and no chain to walk. The reversal carries provenance to the void that created it and is **not** an `ap_ledger_entries` row of manual origin — same carve-out A-36 gives the remainder. *Accepted consequence:* a voided settlement that emitted a remainder leaves two rows that net to zero and sit in the ledger until a Manager clears them under d15, so `ap_clearings` is load-bearing rather than optional |

| A-33b | **An Invoice's `paid` state is derived, never stored.** **Completes A-33 and A-33a**, which said when immutability attaches and releases without saying what the system consults to know. ## 3. Shape

```
Browser (PWA)                Vercel                     Supabase
─────────────                ──────                     ────────
Till / back-office     ──▶   Next.js App Router   ──▶   Postgres
  client components            Route Handlers             ├─ RLS on JWT store_id
  reads: supabase-js           Server Actions             ├─ SECURITY DEFINER functions
  writes: functions only       Cron (/api/cron/*)         └─ review_flags
  print: window.print()        Catalog adapter
                                 ├▶ MusicBrainz + Cover Art Archive → release_cache
                                 └▶ Discogs (implemented, off by default)
                               Resend ──▶ receipts, PurchaseOrders, claims
```

**Reads** go from the client straight to row-level-security-protected views — no server hop, so the till stays fast.
**Writes** go through a typed wrapper to a database function. Never a direct table write.
**Identity** rides in the JWT as `store_id` and `terminal_id`. Every function takes `p_actor_user_id` **and** the `p_actor_initials` it was resolved from; manager-only functions also take `p_manager_user_id` and `p_manager_initials`, and record both names (A-55, amending this sentence's initials-only form). **The id is what the function trusts and the initials are what it displays** — [M-04](flows/M-04-manage-users.md) d16 releases a deactivated User's initials to a new hire, so a string alone resolves to a different person over time. `actor_resolve` is the only place a string becomes a person.

### 5.1 Rules the schema has to enforce

**On hand is derived, and can go negative.** A view, never a column:

```
on_hand   = count(items where status in ('sellable','held'))
          - count(items where origin = 'oversold' and reconciled_at is null)
available = count(items where status = 'sellable')
```

**None of this applies to a non-tracked entry.** An entry whose `tracks_stock` is false ([E-05](flows/E-05-sell-a-record.md) d17, [M-06](flows/M-06-settings.md) d29) has no InventoryItems, is absent from both derivations, is never reported below minimum, and **never mints an oversold item**. Stated because the rules above are otherwise universal: without the exemption a `FREIGHT` line drives stock negative and raises a `negative_stock_sale` flag on a thing that has no stock, which is E-05 d17's *"never warn about negative inventory"* read backwards. `tracks_stock` is an **entry** property taking its Section's default at creation and never re-reading it (M-06 d29) — deliberately unlike the configuration beside it, which is resolved live (d31).

When a Sale outruns stock on a **tracked** entry (E-02 d21), `sale_tender` mints an InventoryItem with `status='sold', origin='oversold'` and raises a flag. This keeps [PRD](PRD.md) §4.1's rule literally true, produces a genuinely negative figure, and leaves [E-04](flows/E-04-manage-inventory.md) reconciliation a concrete row to clear when the real copy arrives.

**An item's provenance is a reference, not a label** (A-45). `inventory_items.invoice_line_id` is nullable and composite-keyed; the Invoice is one join away and the Supplier two, and neither is stored on the item. Null means the copy was not received on any Invoice — true of an oversold copy until it is reconciled, and the only state in which a copy has no paperwork behind it. A rendered string such as `FAB1 55021` is display, computed at read time, and is never what another query joins on.

**Balances are derived from movements and never edited.** A Customer's account balance is a view over `customer_ledger`. One signed figure, as [E-07](flows/E-07-manage-customers.md) requires.

**An Invoice's balance owing** (A-36) is its reconciled **Total** — tax **included**, because A-29 removes tax from *cost of goods*, not from what is owed — less every `ap_payment_targets` row against it in a batch with no void, of **either** `settle_kind`:

```
settled(inv)       = Σ targets on inv, in non-voided batches, money AND claim_credit
balance_owing(inv) = invoice_total(inv) - settled(inv)
paid(inv)          = finalized and balance_owing(inv) <= 0 and settled_count(inv) > 0   -- A-33b
```

**A Supplier's balance** is four terms, and every one of them earns its place:

```
supplier_balance = Σ debits                                  -- finalized Invoices at Total, plus
                                                             -- ap_ledger_entries by type (d14):
                                                             -- Invoice/Consignment +, Adjustment ±, Credit and Claim 0
                 - Σ targets where settle_kind = 'money'
                 - Σ targets where settle_kind = 'claim_credit'
                 - Σ credits that are AGREED (d26) and NOT CONSUMED (A-37)
```

A claim credit enters that fourth term at **the amount its credit memo grants** ([E-04](flows/E-04-manage-inventory.md) d20), which `supplier_claims` records alongside the claim total — the memo is the point of truth and the two commonly differ. At the **Supplier** level a credit reduces the balance whether it is attached or not, and attaching is a re-labelling; at the **Invoice** level only an attached credit reduces that Invoice. That one sentence is the whole of [M-05](flows/M-05-accounts-payable.md) d26, and it is why d26's *"applying a credit never moves the balance"* comes out true: attaching moves an amount from the fourth term into the third. Drop any term and one of M-05's worked examples breaks.

**Both balances may be negative** (d25, A-33b). A negative Supplier balance means **the supplier owes the store** — from a Credited claim larger than what is outstanding, a remainder Credit, a manual Credit, or a decreasing Adjustment. A negative Invoice balance means it was overpaid, and what artifact *that* emits is M-05's open question. Nothing clamps either at zero, and every surface reporting a balance renders a negative one.

**An Invoice's `paid` state is derived** (A-33b) — finalized, balance owing at or below zero, and at least one settlement landed on it. No `status = 'paid'` column: nobody sets it, so storing it would be a second copy of a fact the schema can answer (A-35). The third clause keeps a zero-total Invoice correctable rather than born immutable.

**Backorders are derived** (A-20a) — ordered minus received across every Invoice. No `backorders` table.

**A credit's terminal states are derived** (A-37). **Consumed** is the existence of a claim-credit target in a non-voided batch; **cleared** is membership of a non-voided clearing. No `applied`, `remaining`, `consumed_at`, `cleared_at`, or state enum on a credit. The two are different kinds of fact — one moves money, the other is balance-neutral by [M-05](flows/M-05-accounts-payable.md) d15 — so they are never one column.

**No running totals, anywhere on the payables path.** Four back doors, all tempting and all closed: `invoices.paid_to_date` (M-05 step 2 and d4 both say an Invoice "carries paid to date" — that is a column in the **view**, never in the table); `suppliers.balance` (M-01's own requirement already says the figure is derived); `voided_at` on a batch or a clearing (an update to a row A-33a forbids updating); and `cleared_*` columns on a ledger entry.

**A credit attaches in at most one non-voided batch**, and the equality `Σ targets(c) + Σ remainders emitted from c = amount(c)` holds per credit (A-37). Neither is expressible as a table constraint, so **`ap_settle` is the only enforcement point** — which is A-4 doing real work rather than ceremonial work. Both it and `ap_batch_void` take the credit row `FOR UPDATE` and re-evaluate under the lock: whole consumption removed the arithmetic, not the lock, and a status check without one is how two settlements spend the same credit twice at full value.

**A claim credit may only target an Invoice of the same Supplier** ([M-05](flows/M-05-accounts-payable.md) d7) — declarative, via A-36's composite `(supplier_id, …)` foreign key rather than a check inside a function.

**Every payables artifact carries an actor and a timestamp**, and the manager-only ones carry both names (A-28a, [PRD](PRD.md) §5). Three had nowhere to record one before A-36: the **void**, the **clearing**, and the **remainder Credit** — the last emitted by the system inside a settlement, so it inherits that settlement's actor and Manager. That is written down because the one artifact on the money path nobody consciously creates is the one most likely to end up anonymous.

**Cost of goods excludes inbound tax** (A-29). Per-item cost stays `Ext. Price` alone (E-02 d16), so M-03's unallocated-cost caveat still applies.

**Sale line values are snapshot columns, not joins.** Title, artist, grade, price and discount are copied onto the SaleLine at time of sale (E-05 d13), so a later catalog edit cannot rewrite history. **Tax is snapshotted as per-tax figures — the tax types resolved and the rates applied — never as a reference to a tax line** ([M-06](flows/M-06-settings.md) d11, d16; §5.1's tax paragraph below). A reference would point at a mutable configuration row and break M-06 d8's never-retroactive guarantee the moment a rate was edited, and two composition orders that agree on a customer's total can disagree on what is remitted to whom.

**The close stores its own summary** (A-30) as JSON on the CloseBatch.

**Consignment is copied onto the InventoryItem at receipt** (A-26), never joined.

**Rounding is a pre-fill, not a check constraint** (A-24, A-49). No column, trigger, or function rejects an unrounded amount. The suggestion rounds to the **nearest** instance of one configured price ending, ties away from zero (A-49).

**Referenced configuration is deactivated, never deleted.** Users, tax types, tax groups, product tax codes, tenders, Sections, genres and currencies all carry an active flag and none is ever removed ([M-06](flows/M-06-settings.md) d9). Switching off an **unused** tender is a different act from retiring a used one, and d23 keeps them distinct.

**Tax is a lookup on two axes, not a stacked line** ([M-06](flows/M-06-settings.md) d11, which supersedes its d1 and with it the `tax_lines` / `tax_components` shape this section used to describe). A **tax type** is one tax — code, name, `rate_ppm` (A-47), a **tax registration number** shown beside its line on a receipt ([M-06](flows/M-06-settings.md) d48), and a nullable `gl_account` reserved against a chart of accounts that does not exist yet (A-14's pattern). A **tax group** is a jurisdiction or customer class carrying a ShortName. A **product tax code** is carried by a genre, which is mandatory on every sellable thing (d12, d17). A **cell** on `(tax_group, product_tax_code)` names up to two tax types in composition order, optionally compound (d16). Resolution is the Customer's group, else the store default group; then the genre's code; then the cell (d14) — **not** an override of one by the other. A **blank cell** is out of scope and reportable as nothing; a **zero-rate tax type** is taxable at 0% and reportable, and the two are deliberately distinct (d15). A Sale line snapshots **per-tax figures**, not a tax total, because two composition orders can agree on the customer's total and disagree on what is remitted to whom (d16).

**Tender behavior is code; tender names are data.** The behavior is an enum — `cash`, `card`, `store_credit`, `gift_card`, `payout`, `used_credit`, `rounding` — and the name is editable, exactly as M-06 requires. **Several tenders may share one behavior** ([M-06](flows/M-06-settings.md) d22): `Visa` and `Amex` are two `card` rows, because they settle as separate deposits. A tender also carries **active** and a **code reserved for a general ledger** (d23). **`rounding` is system-written and never selectable** (d26) — `sale_tender` appends it so a cash sale's tenders sum to the Sale total after nickel rounding; it is not a button, and the list of tenders and the list of tender buttons are therefore not the same list.

**Returns are negative-quantity SaleLines** ([E-06](flows/E-06-process-a-return.md) d1), not a separate document.

**Immutability is enforced two ways, deliberately.** SaleLines on Closed Sales, voided Sale numbers, and **a SupplierClaim's `claim_number` once assigned** (A-44) raise on update or delete **by trigger** — all three are local facts on the row being written, so a trigger is the cheapest thing that can hold them. A claim number is unique per store and **never reused**: a voided or abandoned claim keeps it forever ([E-04](flows/E-04-manage-inventory.md) d26), so the sequence has gaps and is not a count of anything.

**A claim void is a row, never a column** (A-44), in `supplier_claim_voids` — the same rule and the same reason A-36 gives for `ap_payment_batch_voids` — and it carries the **`claim_number` it retired**, `unique(store_id, claim_number)` (A-46). ~~A voided claim is finished by the presence of a row, while an abandoned one is finished by the status it carries; a query asking whether a claim is live has to consult both.~~ — **superseded by A-46**: a void **returns the claim to unsent** ([E-04](flows/E-04-manage-inventory.md) d29), so the only terminal states are `Credited` and `Abandoned` and both are statuses. A claim may retire several numbers over several sends, which is why the key is the number and not the claim.

**A derived state keys on a system-written fact** (A-43). Where a state is the presence or absence of a value — a claim's sent date, an Invoice's settlements — that value is one the system writes, never one a user-facing path edits.

**Three till refusals are write-path checks with no trigger and no client enforcement**, on A-4's terms — an invariant enforced only in the screen is not enforced. `sale_void` and `sale_edit` **refuse while a Sale's tenders do not net to zero** ([E-05](flows/E-05-sell-a-record.md) d31): the money must be refunded, moved to the Customer's account, or struck first, and striking a settled tender really does move money (d32), which is why the check is in the function that moves it. A Return additionally **refuses while any returned copy is still routed** ([E-06](flows/E-06-process-a-return.md) d10). All three were recorded in their flows and in no enforcement point, which is the gap this closes.

**An Invoice is different: it is a check in the write path, not a trigger** (A-41). Every write path against a finalized Invoice calls **`invoice_is_paid(invoice_id)`** and refuses while it is true. The predicate is A-33b's — finalized, balance owing at or below zero, at least one settlement landed — and it is **derived, never a stored flag**, so voiding the PaymentBatch that settled it ([M-05](flows/M-05-accounts-payable.md) d22, A-33a) releases the Invoice with nothing to flip. A check written to fire at finalize, or written so that it can never release, is wrong in both directions. Because the predicate spans tables, a path correcting an Invoice locks its row and re-evaluates rather than trusting a value read earlier in the transaction — and `ap_settle` takes the same lock from the other side (A-38). 

**User administration (A-55).** Three invariants, and where each lives:

- **Initials are unique among a Store's active Users** — a partial unique index on `users (store_id, initials) where active`, over values trimmed and upper-cased on write ([M-04](flows/M-04-manage-users.md) d13, d16, d20). Declarative, because unrepresentable beats remembered; the function still traps the violation so the Manager is told which name clashed rather than seeing a constraint error.
- **A Store always has at least one active Manager** ([M-04](flows/M-04-manage-users.md) d14) — **not** a constraint. It is a per-Store aggregate across rows, so no row `CHECK` and no index can hold it, and a stored count is refused by the no-running-totals rule above and by A-35. It is asserted inside `user_change_role` and `user_deactivate`, which take the Store's active Manager rows `FOR UPDATE` in primary-key order (A-38) and re-count under the lock. Without the lock, two Managers demoting each other concurrently both read a count of two and both commit.
- **Who changed a role, and from what** — `users` carries a `log`, the column A-35 mirrors from Invoices and Suppliers, appended by all four user functions with actor, authorizing Manager, timestamp, and the values **before and after** (A-52's reasoning, transferred).

## 6. Database functions

Every function takes `p_actor_user_id` and the `p_actor_initials` it was resolved from. Functions marked **M** are manager-only and also take the authorizing Manager's id and initials, recording both names (A-28a, A-55). The id is what is trusted; the initials are what is displayed. Nothing else blocks — actions worth a second look raise flags instead.

**Pure helpers**, which encode the pricing rules and are the highest-value tests in the system:

- `round_to_ending(minor bigint, ending_minor bigint) → bigint` — rounds to the **nearest** instance of one configured price ending, **ties away from zero** (A-47). The ending is an integer of minor units (`99`, `95`, `0`) held in `store_settings` and passed **as an argument**, so the helper stays pure. Advisory: no column, trigger or function rejects an unrounded amount (A-24, A-49). ~~`round_up_shelf(minor)`~~ — renamed and reversed by A-49; the old name said always-up, which is no longer what it does.
- `suggested_retail(list_minor, margin_ppm) → minor` — priced off the pre-discount list price ([E-02](flows/E-02-receive-inventory.md) d49; `_bp` → `_ppm` per A-47). E-02 d8, which this line used to cite, is struck.
- `upc_a_check_digit(text) → text`.

**`invoice_is_paid(invoice_id) → boolean`** is the single definition of A-33b's predicate and the seam A-41 puts immutability on. It is read-only and derived: finalized, balance owing at or below zero, and at least one settlement landed on it. **M3 ships it returning `false`** — true of every Invoice until payables exists — and the payables milestone replaces the body. Every write path against a finalized Invoice calls it and refuses while it is true; `ap_settle` and `ap_batch_void` call it when they re-evaluate; the screens call it to decide whether to draw the scan slab.

**Scan resolution** is read-only: `resolve_scan(p_code)` branches on a `GC` prefix, a non-tracked item code, an internal barcode (resolving to exactly one InventoryItem), or a manufacturer UPC (resolving to a Record, returning a picker payload when sellable copies differ).

`ap_settle` is the heaviest of the payables functions and has the same shape (A-38). In one transaction it validates that every ticked row belongs to one Supplier in one Store, writes the PaymentBatch, writes one target per debit and kind, records any Claim placeholder disposals, emits the remainder Credits [M-05](flows/M-05-accounts-payable.md) d28 requires, asserts A-37's per-credit equality, re-evaluates A-33b for every Invoice it touched, and returns any flags. All or none. It locks **every credit and every debit in the selection `FOR UPDATE`, in primary-key order** — the order matters, because two Managers ticking the same rows in opposite screen order would otherwise deadlock, and `sale_tender` avoids that by always taking the counter first while payables has no counter to anchor on. It locks **nothing on the Supplier row**: the balance is derived and stored nowhere, so there is nothing to serialise. A credit-only settlement carries no payment reference (d19).

`ap_batch_void` appends the void artifact and never updates the batch (A-33a). It restores every credit by the **absence** of a live target rather than by a write (A-37), and for every remainder the batch emitted it **appends a reversing Adjustment** rather than deleting it (A-42) — so the void never refuses, whatever became of that remainder afterwards, and there is no chain to walk. Double-void is prevented declaratively by `unique(batch_id)` rather than by a status check.

`sale_tender` is the heaviest function overall and the most important. In one transaction it verifies the lock, allocates the Sale number from the locked counter, marks items sold, mints oversold items, raises any flags, debits gift cards, writes the customer ledger, moves the Sale to Current, and queues the receipt email. It either all happens or none of it does. It accepts zero lines — that is how a deposit (A-25) and a `$0.00` Used Credit counter buy are both rung.

`packages/contracts` is the interface between the two workstreams. For each database function it holds an input schema, an output schema, and a typed wrapper. It is written first, jointly. The screen developer builds against it with an in-memory fake while the database developer implements the function to satisfy it, so neither waits on the other. **A change to a contract is a pull request both review** — that is the only coordination ritual this architecture imposes.

## 10. Risks

| Risk | Response |
|---|---|
| **MusicBrainz coverage of vinyl** | The licence risk is gone (A-12); coverage replaces it. Discogs is deeper on vinyl because collectors built it, and pressing variants are where it wins. M2 measures this against roughly 200 real barcodes off the shelf. Below about 85%, switch the adapter's default and re-open the licence question. Manual entry (E-02 step 9) catches misses either way, at the cost of receiving time. |
| **Reserved GL columns, and a deferral that now leans on them** | Four columns exist to be filled by a chart of accounts that does not exist — `tax_types.gl_account` ([M-06](flows/M-06-settings.md) d11), a tender's code (d23), a Section's GL code (d28), and A-14's `cover_art_path` on the same pattern. Nothing reads one, nothing validates one, no migration waits on one. That was cheap while it was housekeeping. **M-06 d39 changed what it costs:** exchange gain or loss is now deferred *because there is no ledger to post it to*, so a real money computation is queued behind a chart of accounts nobody has scheduled, and *reserved* has quietly become *scheduled*. Response: leave them nullable and undrawn, and treat the chart of accounts as a flow to be written rather than a field to be filled. When it is written, re-check all four shapes — a column reserved against an unwritten specification is a guess with a comment on it. |
| **Settings that do nothing in v1** | M-06 ships three: the cash drawer (d25 — *"a setting that does nothing"*), receipt width (d50 — *"wrong in a way nothing can detect"*, there being no print agent to report back), and the logo URL (d49, which an email client will block). Each names its own consequence; none is visible as a class. The class risk is that a settings screen with three inert controls teaches staff the screen is decorative, and the fourth control they ignore will be a live one. Response: draw them as explicitly pending rather than as working controls. |
| **Flags accumulating unread** | A review queue nobody opens is worse than a gate, because it looks like oversight. A-49 adds a case worth watching: rounding **down** can suggest a price below cost, so E-02 d35's flag can fire on a figure the system itself proposed — which is exactly the flag that trains people to acknowledge without reading. Surface the unreviewed count in the app shell from M1 and check it during the pilot. |
| **Emailed receipts** | A walk-in paying cash with no email address gets nothing without the browser-print fallback, so build it in M5 rather than deferring it. Watch deliverability — a receipt in a spam folder is a customer-service problem. |
| **Cover art as a URL** | Still in tension with E-02 d6's one-time snapshot, though Cover Art Archive URLs are stable and openly licensed. `cover_art_path` is reserved so a snapshot job is an addition, not a migration. |
| **Per-Store catalogs multiplying lookups** | The shared cache (A-6) absorbs it. Worth monitoring the hit rate once a second Store exists. |
| **Online-only stops trading in an outage** | Accepted (A-1). The card terminal is independent of this system, so a genuine outage already halts card sales. Revisit only with evidence from the pilot. |
| **Backups** | Mostly a plan-tier setting rather than build work — Supabase Pro includes daily backups with a 7-day retention window, and point-in-time recovery is an add-on. Enable it at launch and verify a restore in M6, because an unverified backup is a guess. |

## 11. Open questions

~~**One is blocking.** §5.1's immutability trigger ships in M3 while payables ships post-v1.~~ **Closed by A-39:** the trigger moves to the payables milestone, where its predicate is evaluable and where it first has an Invoice to guard. It was never a question of faking the predicate in M3 — no Invoice can reach *paid* that early, so the trigger protected nothing there either.

~~**Nothing is blocking now.**~~ — **§8 scheduled no milestone for the configuration tables** while M4's till cannot compute tax without them. **Closed by A-53**, which lands them in M1 and M2 and leaves only the settings screens post-v1.

**Nothing is blocking now.** Of the four questions the settings session opened, **two are now closed** and two are unanswered; none of them stops a build:

- ~~**Who may write a Store's ID and position?**~~ — **Closed by [M-04](flows/M-04-manage-users.md) d11: nobody, and no role is added to hold it.** Both fields are assigned by the WaxWorks team when a Store is set up, alongside its authentication provisioning, and there is no screen, function, or role that changes them afterwards. **So A-52's exemption of these two fields is permanent rather than a placeholder**, and §6 is right to offer no function — the *function* half was never the open part. The question read as a hole in the role model because settings are manager-only under A-28a and these two fields are not; it is not a hole, because the write happens **before the shop exists as a tenant**, which puts the actor outside the role model rather than above it. M-04 d14 disposes of the other half of its *tier above Manager* question with a floor rule rather than a role, so **no Owner tier exists anywhere in the model** and none is coming. *Consequence carried over from M-04 d11:* a wrong Store ID or position has no in-shop correction path and is a support conversation, so the assignment has to be right first time.
- ~~**Does A-28a's *"deletions"* mean what [E-07](flows/E-07-manage-customers.md) d12 says it does not?**~~ — **Closed by A-54**, which was written in the same session as this question and answers both of its halves. Deletion is gated by **state, not role**, so A-28a's unnamed *deletions* category is superseded and E-07 d12's ungated Customer survives whole; and A-28a's list gained the four actions it was missing — processing pending orders into PurchaseOrders, voiding a PurchaseOrder, and abandoning or voiding a claim. [M-01](flows/M-01-supplier-margin.md)'s question narrows to whether a Supplier with nothing in flight is a Manager's to delete, with the destructive case impossible at either answer. **This bullet outlived its answer** and is struck rather than deleted, because the question is a fair thing to have asked.
- **A tax rate edited in place now moves every jurisdiction at once.** `tax_types.rate_ppm` is the single row every tax group reads (M-06 d11), and [E-05](flows/E-05-sell-a-record.md) d13's snapshot is the only thing standing between an edit and a restated history. M-06 carries the versioning question; what it has not recorded is how narrow that margin is. **Owns:** M-06; §5 absorbs the answer.
- **Does the receipt email fetch a Manager-supplied URL server-side?** M-06 d49 makes the logo a URL and requires the email to **embed** it. Embedding means something fetches an arbitrary URL on the Resend path (A-8), and no document says where that fetch runs. **This is a suspicion rather than a finding** — it is the only new external-input surface this session created. **Owns:** §4.

The rest below are **not blocking** but are unanswered, and all were surfaced by [M-05](flows/M-05-accounts-payable.md) d18–d22:

- ~~**Is an Invoice's `paid` state stored or derived?**~~ **Answered: derived** (A-33b). The release in A-33a is therefore automatic rather than a step, and the M3 trigger evaluates the predicate rather than reading a flag.
- ~~**Where is the sum of a claim's applications bounded?**~~ **Answered, by removing the case rather than enforcing it.** [M-05](flows/M-05-accounts-payable.md) d24 supersedes d20: a SupplierClaim is applied **whole or not at all**, so there is no running remainder and no sum to bound. The concurrency question collapses from a money invariant needing a row lock in two paths to a **status check** — is this claim already applied. Where a credit exceeds what is owed, the excess is emitted as a separate **remainder Credit** artifact (d25), which is an append rather than a mutation and races with nothing.
- ~~**The Payables schema no longer matches what M-05 requires.**~~ **Answered by A-36**, which replaces §5's table group and both balance derivations, retires `ap_payments`, and gives manual ledger entries and the remainder Credit the tables they never had. §5's *principle* — balances derived from movements, never edited — was never the stale part; the inputs were.
- **Does a payables action deserve a `review_flags` kind?** §5.2's `kind` enum has no payables value, and a ReviewFlag is defined as a record that an *Employee* did something worth a Manager's attention. So in a single-Manager store the Manager who records a payment is the one who can void it, and nobody is told. This follows from A-28a as written rather than contradicting it — flagged as the place where "audit matters most where the money is" lands, not as a defect.
- ~~**Do `SECURITY DEFINER` functions re-assert `store_id`?**~~ **Answered by A-40**, with A-36's composite `(store_id, id)` foreign keys as the structural backstop.
